# I/O

## Qué abarca
- Input/output
- dispositivos y streams

## Mis notas

## Objetivo
Utilizo I/O para mover datos entre el espacio de usuario y los dispositivos del sistema, ya sea un disco, una terminal o una tubería entre procesos. Resuelvo el problema de cómo un programa accede a recursos externos de forma controlada, evitando bloqueos inesperados y garantizando la integridad de la información. En mi día a día como ingeniero Linux senior, empleo I/O al inspeccionar logs, montar sistemas de archivos, depurar servicios con `strace` o diseñar demonios que procesan flujos continuos. Cuando entiendo los mecanismos de I/O puedo escribir scripts y programas que gestionen recursos eficientemente, diagnosticar cuellos de botella de disco o red, y elegir la API adecuada (bloqueante, no bloqueante, asíncrona). No necesito preocuparme por I/O cuando mi tarea es puramente cálculo interno sin interacción con archivos, sockets o dispositivos.

## Esqueleto (el 20% esencial)
1. **I/O como flujo de datos**: cualquier interacción con dispositivos o archivos se modela como un stream de bytes.  
2. **System calls de bajo nivel**: `open`, `read`, `write`, `close` crean y manipulan file descriptors que representan esos streams.  
3. **Bloqueo vs no‑bloqueo**: por defecto las operaciones son bloqueantes; la bandera `O_NONBLOCK` permite que el proceso continúe mientras el kernel espera datos.  
4. **Redirección y pipelines**: la shell conecta streams mediante `|`, `>`, `<`, facilitando la comunicación entre procesos (IPC).  

## Como funciona
1. El proceso llama a `open()` indicando el pathname y flags; el kernel asigna un file descriptor y crea una estructura interna que enlaza al dispositivo o archivo.  
2. Cuando se invoca `read(fd, buf, n)`, el kernel copia hasta *n* bytes desde el buffer del dispositivo al buffer de usuario `buf`. Si no hay datos disponibles y el descriptor es bloqueante, el proceso se suspende.  
3. Con `write(fd, buf, n)` ocurre lo inverso: los bytes del proceso se copian al buffer del dispositivo; el kernel gestiona la escritura física o la entrega a otro proceso.  
4. Al cerrar con `close(fd)` el kernel libera el descriptor y cualquier recurso asociado.  
5. En pipelines, la salida de un proceso (`stdout`) se redirige a la entrada (`stdin`) de otro mediante un pipe creado con `pipe()`, y ambos procesos comparten los extremos del pipe como descriptors.

## Detalles
- **Básico**: uso de `open/read/write/close` en C o comandos de shell (`cat`, `echo`).  
- **Intermedio**: manipulación de flags (`O_RDONLY`, `O_WRONLY`, `O_CREAT`), control de buffering con `setvbuf()` en la biblioteca estándar, y uso de `select()`/`poll()` para esperar datos en varios descriptors.  
- **Avanzado**: APIs de I/O asíncrona como `aio_*`, `epoll` para gran número de sockets, y `io_uring` que delega la preparación y finalización de operaciones al kernel, reduciendo copias de datos y context switches.  
- **Buffering**: la capa de libc (`stdio`) introduce un buffer interno que reduce llamadas al kernel; sin embargo, para alta performance se prefieren los descriptors sin buffering o se controla explícitamente con `fflush()` y `setbuf()`.

## Ejemplo minimo
```c
#include <fcntl.h>
#include <unistd.h>

int main() {
    int fd = open("/tmp/ejemplo.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644);
    write(fd, "hola\n", 5);
    close(fd);
    return 0;
}
```
Este programa crea (o trunca) el archivo `/tmp/ejemplo.txt`, escribe la cadena `hola` y cierra el descriptor. La salida esperada es que el archivo contenga esa línea.

## Errores comunes
- No comprobar el valor de retorno de `read`/`write`; puede indicar error o lectura parcial.  
- Olvidar cerrar descriptors, provocando fugas de recursos.  
- Usar `O_NONBLOCK` sin manejar `EAGAIN`, lo que lleva a bucles de espera ocupada.  
- Mezclar buffers de `stdio` y descriptors sin sincronizar (`fflush`).

## Estado actual
Los conceptos básicos de I/O (file descriptors, `read`/`write`, bloqueo) son estables y forman parte del estándar POSIX. En la práctica moderna, los administradores y desarrolladores prefieren APIs como `epoll` para multiplexar cientos de sockets y `io_uring` para minimizar la sobrecarga del kernel en aplicaciones de alto rendimiento. Estas técnicas están ampliamente soportadas en distribuciones Linux actuales.

## Conexiones
- **System Calls**: `read`, `write` y `open` son llamadas al kernel que implementan el mecanismo de I/O.  
- **Processes IPC**: los pipes y sockets son streams de I/O que permiten la comunicación entre procesos.  
- **Filesystem**: cada archivo del sistema se accede mediante I/O; la estructura de directorios y los metadatos se gestionan con las mismas llamadas.

## Ruta de estudio
1. **Prerequisitos**: familiaridad con la línea de comandos de Linux, conceptos de procesos y programación en C.  
2. **Fundamentos**: practicar `open/read/write/close`, entender los modos de apertura y los permisos de archivo.  
3. **Multiplexado**: aprender `select` y `poll`, luego `epoll` para escalabilidad.  
4. **I/O asíncrona**: explorar la API POSIX AIO y, posteriormente, `io_uring`.  
5. **Optimización**: estudiar el impacto del buffering, alineación de bloques y técnicas de zero‑copy.
